PADROES DE PROJETO NO PROJETO NANASMART
========================================

Objetivo
--------
Este documento analisa onde os padroes Singleton, Builder, Factory Method e
Abstract Factory poderiam ser usados neste projeto Django, por que seriam
uteis e quais deles fazem sentido adotar.

Importante: este arquivo e apenas uma proposta arquitetural. Nenhum codigo
existente foi alterado.

Resumo da recomendacao
----------------------

1. Builder: RECOMENDADO para a montagem dos prompts enviados a IA.
2. Factory Method: RECOMENDADO para escolher o exportador pelo formato.
3. Abstract Factory: OPCIONAL, caso o sistema passe a ter familias de
   exportacao (por exemplo, relatorio simples, relatorio executivo e relatorio
   tecnico em CSV/Excel/PDF).
4. Singleton: NAO RECOMENDADO como implementacao manual neste momento. O
   Django ja possui gerenciamento de configuracoes, aplicativos e conexoes.
   Se houver necessidade de reutilizar o cliente Gemini, pode-se usar um
   cache controlado, mas isso nao precisa ser um Singleton classico.


1. BUILDER - CONSTRUCAO DE PROMPTS DA IA
========================================

Onde usaria
-----------
No pacote gemini_api, principalmente substituindo a montagem direta dos
prompts em prompt_builder.py. Os metodos atuais
build_chat_prompt(), build_os_analysis_prompt(),
build_unassigned_orders_prompt() e build_finance_prompt() montam textos com
blocos de contexto, instrucoes, resumos, filtros e pergunta do usuario.

Por que usaria
--------------
Um prompt possui muitas partes opcionais e varia conforme o objetivo e o
perfil do usuario. O Builder permitiria montar o prompt passo a passo, sem
espalhar concatenacoes de strings e regras condicionais por varias funcoes.

Beneficios:
- deixa explicita a ordem dos blocos do prompt;
- permite incluir ou omitir alertas, telemetria, ordens e dados financeiros;
- facilita criar novos tipos de analise sem duplicar a montagem do texto;
- permite testar cada combinacao de contexto separadamente;
- reduz o risco de enviar dados fora do escopo do usuario.

Sugestao de participantes
-------------------------
- PromptBuilder: recebe as partes e oferece metodos como
  com_contexto(), com_alertas(), com_ordens(), com_telemetria(),
  com_financeiro(), com_instrucoes() e com_pergunta().
- PromptDirector ou servico de aplicacao: define a sequencia adequada para
  chat, analise de OS e analise financeira.
- Prompt: produto final, uma string pronta para generate_content().

Exemplo conceitual de uso (nao implementado)
---------------------------------------------
prompt = (PromptBuilder()
    .com_contexto(context)
    .com_alertas(context['alert_summary'])
    .com_ordens(context['open_order_summary'])
    .com_pergunta(message)
    .build())

Diagrama de classes
-------------------

Simbolos POO: + publico, - privado, # protegido, {static} membro estatico.
Nas ligacoes: ^-- heranca, ..|> implementacao, --> associacao,
..> dependencia e *-- composicao.

  +----------------------------------+
  | <<interface>>                    |
  | PromptBuilder                    |
  +----------------------------------+
  | +com_contexto(context): PromptBuilder |
  | +com_alertas(alertas): PromptBuilder  |
  | +com_ordens(ordens): PromptBuilder    |
  | +com_telemetria(dados): PromptBuilder |
  | +com_financeiro(dados): PromptBuilder |
  | +com_instrucoes(texto): PromptBuilder |
  | +com_pergunta(texto): PromptBuilder   |
  | +build(): Prompt                       |
  +----------------------------------+
                    ^ ..|>
                    |
  +----------------------------------+
  | PromptBuilderConcreto            |
  +----------------------------------+
  | -blocos: list[str]                |
  +----------------------------------+
  | +com_contexto(context): PromptBuilder |
  | +com_alertas(alertas): PromptBuilder  |
  | +com_ordens(ordens): PromptBuilder    |
  | +com_telemetria(dados): PromptBuilder |
  | +com_financeiro(dados): PromptBuilder |
  | +com_instrucoes(texto): PromptBuilder |
  | +com_pergunta(texto): PromptBuilder   |
  | +build(): Prompt                       |
  +----------------------------------+
                    |
                    | ..> cria
                    v
  +----------------------------------+
  | Prompt                           |
  +----------------------------------+

          PromptBuilder

O Builder e indicado aqui porque o problema principal e construir um objeto
complexo por etapas. O produto nao e uma entidade do banco; e o texto final
enviado para a IA.


2. FACTORY METHOD - EXPORTACAO POR FORMATO
===========================================

Onde usaria
-----------
No app exportacao. Atualmente exportacao/views.py possui _despachar_formato(),
que decide com if/elif entre exportar_csv(), exportar_excel() e exportar_pdf().

Por que usaria
--------------
A view nao deveria conhecer todos os detalhes de criacao de respostas CSV,
Excel e PDF. O Factory Method centralizaria a escolha do produto correto a
partir do formato solicitado.

Uma nova exportacao, como JSON, seria adicionada criando um novo produto e
registrando sua fabrica, sem aumentar uma cadeia grande de if/elif na view.

Sugestao de participantes
-------------------------
- Exportador: contrato comum com exportar(nome, titulo, colunas, linhas).
- ExportadorCSV, ExportadorExcel e ExportadorPDF: implementacoes concretas.
- ExportadorFactory: metodo criar_exportador(formato).
- View: pede um exportador e chama exportar(), sem conhecer a implementacao.

Diagrama de classes
-------------------

  +----------------------------------+
  | <<interface>>                    |
  | Exportador                       |
  +----------------------------------+
  | +exportar(nome, titulo,          |
  |  colunas, linhas): HttpResponse  |
  +----------------------------------+
                    ^
                    | ..|> implementa
        +-----------+-----------+-----------+
        |                       |           |
  +-------------+       +-------------+ +-------------+
  | Exportador  |       | Exportador  | | Exportador  |
  | CSV         |       | Excel       | | PDF         |
  +-------------+       +-------------+ +-------------+
  | +exportar() |       | +exportar() | | +exportar() |
  +-------------+       +-------------+ +-------------+

  +----------------------------------+
  | <<abstract>>                     |
  | ExportadorCreator                |
  +----------------------------------+
  | +exportar(dados): HttpResponse   |
  | #criar_exportador(): Exportador |
  +----------------------------------+
          ^                 ^                 ^
          | ^-- heranca     | ^-- heranca     | ^-- heranca
  +---------------+ +---------------+ +---------------+
  | CriadorCSV    | | CriadorExcel  | | CriadorPDF   |
  +---------------+ +---------------+ +---------------+
  | #criar_       | | #criar_       | | #criar_      |
  | exportador(): | | exportador(): | | exportador():|
  | Exportador    | | Exportador    | | Exportador   |
  +---------------+ +---------------+ +---------------+
          | ..> cria       | ..> cria       | ..> cria
          v                v                v
     ExportadorCSV    ExportadorExcel   ExportadorPDF

O Factory Method e o padrao mais diretamente aplicavel ao codigo atual, pois
ja existe uma decisao centralizada de qual formato deve ser criado. No desenho,
o metodo protegido criar_exportador() e sobrescrito pelos criadores concretos;
essa sobrescrita e o Factory Method.


3. ABSTRACT FACTORY - FAMILIAS DE RELATORIOS
============================================

Onde usaria
-----------
No mesmo app exportacao, mas somente se o projeto precisar de familias de
relatorios com componentes relacionados. Por exemplo:

- familia Operacional: tabela simples e cabecalho operacional;
- familia Executiva: tabela resumida, indicadores e grafico;
- familia Tecnica: tabela detalhada, alertas e observacoes tecnicas.

Cada familia poderia oferecer a versao CSV, Excel e PDF dos mesmos dados e
com a mesma identidade visual/regras de apresentacao.

Por que usaria
--------------
O Abstract Factory garante que os componentes de uma mesma familia sejam
criados juntos e sejam compativeis. Assim, ao selecionar o tipo de relatorio,
a aplicacao nao mistura acidentalmente o cabecalho executivo com o layout
tecnico ou com regras de apresentacao de outra familia.

Exemplo de familias
-------------------
- FabricaRelatorioOperacional cria ExportadorCSVOperacional,
  ExportadorExcelOperacional e ExportadorPDFOperacional.
- FabricaRelatorioExecutivo cria ExportadorCSVExecutivo,
  ExportadorExcelExecutivo e ExportadorPDFExecutivo.

Diagrama de classes
-------------------

  +----------------------------------+
  | <<interface>>                    |
  | FabricaRelatorio                 |
  +----------------------------------+
  | +criar_csv(): ExportadorCSV      |
  | +criar_excel(): ExportadorExcel  |
  | +criar_pdf(): ExportadorPDF      |
  +----------------------------------+
       ^ ..|> implementa       ^ ..|> implementa
       |                       |
  +----------------------+  +----------------------+
  | FabricaRelatorio     |  | FabricaRelatorio     |
  | Operacional           |  | Executivo            |
  +----------------------+  +----------------------+
  | +criar_csv()         |  | +criar_csv()         |
  | +criar_excel()       |  | +criar_excel()       |
  | +criar_pdf()         |  | +criar_pdf()         |
  +----------------------+  +----------------------+
       | ..> cria              | ..> cria
       +-----------+-----------+-----------+
                   |
                   v
  +------------------+  +------------------+  +------------------+
  | <<interface>>    |  | <<interface>>    |  | <<interface>>    |
  | ExportadorCSV    |  | ExportadorExcel  |  | ExportadorPDF    |
  +------------------+  +------------------+  +------------------+
  | +exportar(dados) |  | +exportar(dados) |  | +exportar(dados) |
  +------------------+  +------------------+  +------------------+
       ^ ..|>               ^ ..|>               ^ ..|
       |                    |                    |
  +------------------+  +------------------+  +------------------+
  | CSVOperacional   |  | ExcelOperacional |  | PDFOperacional   |
  +------------------+  +------------------+  +------------------+

  +------------------+  +------------------+  +------------------+
  | CSVExecutivo     |  | ExcelExecutivo   |  | PDFExecutivo     |
  +------------------+  +------------------+  +------------------+
       ..|>                 ..|>                 ..|>
       (implementam as respectivas interfaces de formato)

Relacao com Factory Method
--------------------------
Factory Method resolve uma escolha de um produto, como CSV ou PDF.
Abstract Factory resolve a escolha de uma familia inteira de produtos
relacionados. Por isso, Abstract Factory nao deve ser usado apenas para
renomear o atual if/elif: nesse caso o Factory Method e suficiente.


4. SINGLETON - CONFIGURACAO OU CLIENTE EXTERNO
===============================================

Possivel local
--------------
O candidato mais proximo seria gemini_api/cliente.py, na criacao do cliente
Google Gemini feita por get_gemini_client(). Outra possibilidade seria um
objeto de configuracao de exportacao compartilhado.

Por que pode parecer interessante
---------------------------------
Criar um cliente externo uma unica vez pode reduzir inicializacoes repetidas
e manter uma configuracao comum de API. O acesso poderia ser feito por um
servico compartilhado por generate_content() e pelas demais funcoes de IA.

Por que NAO recomendo implementar agora
---------------------------------------
- o Django ja controla settings e o ciclo de vida da aplicacao;
- clientes globais podem manter estado entre requisicoes;
- testes ficam mais dificeis, pois um teste pode contaminar outro;
- a chave GEMINI_API_KEY e lida do ambiente e pode mudar entre execucoes;
- em processos com multiplos workers, cada processo tera seu proprio
  Singleton, portanto ele nao sera realmente unico no sistema inteiro;
- a funcao atual retorna None quando a chave nao esta disponivel, o que e uma
  politica simples e explicita.

Alternativa mais adequada
-------------------------
Se a criacao do cliente se tornar cara, usar um cache por processo com
invalidacao clara e injecao de dependencia nos servicos. Isso entrega
reutilizacao sem impor um Singleton rigido. O cache deve ser coberto por
testes para os casos de chave ausente, chave alterada e erro de inicializacao.

Diagrama conceitual, caso seja realmente necessario
---------------------------------------------------

  +----------------------------------+
  | <<Singleton>>                    |
  | GeminiClientProvider             |
  +----------------------------------+
  | -{static} instance:              |
  |  GeminiClientProvider            |
  | -client: GeminiClient            |
  +----------------------------------+
  | -GeminiClientProvider()          |
  | +{static} get_instance():        |
  |  GeminiClientProvider            |
  | +get_client(): GeminiClient      |
  +----------------------------------+
                    *-- composicao
                    |
                    v
  +----------------------------------+
  | GeminiClient                     |
  +----------------------------------+
  | +generate_content(...): Response |
  +----------------------------------+

Simbolos POO usados neste diagrama:
- - atributo ou operacao privada;
- + operacao publica;
- {static} membro da classe, compartilhado pela classe;
- *-- composicao: o provider controla a instancia do cliente;
- <<Singleton>> estereotipo que identifica o padrao.

Esse diagrama representa uma alternativa futura, nao uma mudanca recomendada
para a versao atual.


CONCLUSAO
=========

Para a entrega atual, eu usaria dois padroes:

- Builder em gemini_api/prompt_builder.py, porque os prompts sao montados por
  varios blocos opcionais e possuem diferentes objetivos.
- Factory Method em exportacao/views.py, porque a escolha CSV/Excel/PDF ja e
  uma fabrica natural escondida em _despachar_formato().

Eu deixaria Abstract Factory documentado como evolucao futura, ativando-o
apenas quando existirem familias de relatorios relacionados. Tambem nao
forcaria Singleton: padroes devem reduzir acoplamento e complexidade, e neste
caso um Singleton manual provavelmente aumentaria ambos.

Prioridade sugerida:
1. Factory Method para exportadores.
2. Builder para prompts.
3. Abstract Factory quando surgirem familias de relatorios.
4. Singleton somente mediante uma necessidade comprovada de ciclo de vida e
   cache, com testes de isolamento.
